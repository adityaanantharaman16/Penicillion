## Next work, in order

1. **Local corpus pilot.** Start from the shipped release, build the held-out answer set, measure current coverage, then prepare a reviewed open-pool candidate. Save the inventory, examples of corrected misses, unsafe near-matches and repeat simulations with the release. The larger editorial milestones can continue independently of hosting.
2. **Local hosting preparation.** Once asked to implement, start with production ingress, secrets and scoped database access. Use two actors and two workers to verify ownership, revocation and timers. Cache repeated reads after profiling. See the [hosting and security plan](HOSTING-PLAN.md) for policy by table and endpoint.
3. **Owner decision on a pilot.** Present the live quote for a New York pilot, expected audience, single-node outage tolerance, authentication choice and staging budget. The recommendation is roughly $69/month base for one environment. Google OIDC already fits the pilot.
4. **Approved staging, then a separate launch decision.** Submit external load results, a restored backup, the cost estimate and a rollback plan before asking to open public traffic. Revisit data-store redundancy, capacity and managed authentication as demand becomes measurable.

For a fresh chat, specify which milestone you want it to execute. The plans are proposals. The owner requested documentation only for this handoff and has not approved cloud spend, staging, public deployment or DNS changes.
