# Historical proposal for Supabase Realtime

Superseded on 12 November 2026. The selected DigitalOcean Droplet runs the existing WebSocket server, Redis and timer loop. The proposal below is archived for reference. For active work, follow the [Droplet setup guide](DIGITALOCEAN-SETUP.md).

## Reuse the current game contract

The browser already sends commands over HTTP with a command ID and expected epoch. The native WebSocket delivers personalized state. PostgreSQL locks the room and commits state, events, affected seats and command receipts together. The present worker uses Redis to notify peers and a half-second sweep to advance unattended rooms. Reuse the command path, rules, receipts, personalized snapshot builder and arena. Replace the subscription, presence and scheduling mechanisms. ## First milestone: two private seats

1. **Establish identity.** Keep the existing guest and signed-in sessions as the authority. Prototype a same-origin token endpoint that checks the cookie, current membership and socket budget and issues short-lived credentials accepted by Supabase Realtime. Verify a supported signing-key or issuer integration against the target project. Map the existing text principal and current seat occupancy to trusted claims. Mint only the low-privilege client role. Keep signing keys server-side. Refresh after rechecking membership and test logout, guest claim and token expiry. If the token bridge cannot enforce these rules, record what failed before proposing an auth migration. [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization) · [JWT signing keys](https://supabase.com/docs/guides/auth/signing-keys)
2. **Deliver committed updates.** Use a private Broadcast topic per room, disable public channel access and require a read policy on realtime.messages. Deny client broadcasts. A transactional database trigger can send an opaque version-change signal when the room version advances. Exclude answers, deadlines, session data and personalized snapshots. After subscribing, fetch the current view through the authorized HTTP API. Coalesce bursts and refetch after reconnect, tab resume or a missed update. Keep bounded resync and the browser's stale-version guard. Channel permissions may be cached until token refresh. On membership change, rotate the topic generation or use equivalent tested revocation so a former seat cannot observe subsequent activity. [Database Broadcast](https://supabase.com/docs/guides/realtime/broadcast) · [Client synchronization](../web/relay.js)
3. **Preserve time and presence.** Keep the fuse in PostgreSQL and check the authoritative deadline in every command under the room lock. Prototype a one-second Supabase Cron check for due work. Dispatch a bounded authenticated settlement job only when rooms need it, with deduplication, retry and monitoring. Reuse the existing room mutation logic for both scheduled and request-driven settlement. Measure actual dispatch delay and stop duplicate jobs from costing two lives. Concurrent answers must observe the same expiry rules as today. Run this case with both tabs closed. Keep server-verified heartbeats for the 14-second reconnect indication and 45-second forfeit. Refresh the three urgency cues across their thresholds even when the room version stays constant, while keeping the exact fuse private. Clean up abandoned rooms and expired leases. [Cron scheduling](https://supabase.com/docs/guides/cron) · [Timing and recovery rules](../ops/ARCHITECTURE.md)
4. **Playtest the prototype.** Use two independent browser profiles and a third unauthorized identity. Create, join, ready, pass, disconnect, reconnect and time out. Submit an answer at expiry and replay its command ID. Verify a single persistent result and the same lives, charge and holder on both screens. Interrupt delivery after commit and recover from a snapshot. Attempt private subscriptions, spoofed broadcasts, guessed room reads, expired tokens and re-entry using a departed seat's receipt. Treat a leaked private view or duplicate pop as a failed milestone.

## Complete the pilot

- Restore Quick match, invited starts, spectators, rematches and 2–8 seats. Check duplicate concepts, category exhaustion, last survivor and extra-life thresholds. Keep the existing gestures, animations and input behavior. Test in two-, five- and eight-seat rooms and include a phone browser. [Independent playtest baseline](../evidence/relay-arena/PLAYTEST.md) · [Browser coverage](../scripts/ci/relay.browser.mjs)
- Move create/join, guessing, room command, actor answer and connection limits to shared storage. Track expiring subscriptions per actor including multiple tabs. An authenticated heartbeat must never renew a departed seat. Recheck authorization on each snapshot and command. [Security and limits](HOSTING-PLAN.md)
- In approved staging, exercise overlapping Vercel invocations, slow mobile reconnects, token refresh, a delayed or repeated scheduled job and a missed notification. Check the existing cancellation rule after a service outage longer than 30 seconds past a fuse. Record answer-to-peer latency separately from scheduled expiry delay. Proposed targets are p95 under 500 ms for committed passes reaching peers, p95 under two seconds for visible timeout settlement, and zero duplicate scoring or unauthorized state reads. These are targets to measure, not hosted results.
- Run the existing local tests and the new transport path against identical game scenarios. At 30 mixed concurrent players for 30 minutes, record query/connection pressure, Realtime message fan-out, token requests, throttling and scheduled job volume. Confirm the environment fits the proposed Supabase tier. Rehearse rollback between compatible versions, draining active rooms if transport versions cannot coexist. Share the evidence before asking the owner to enable public traffic.
