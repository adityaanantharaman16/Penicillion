## Request path and data

| Layer | How it works |
| --- | --- |
| Domain and access | Cloudflare Registrar and DNS host the apex A record for the Droplet (DNS only). The owner selected a shareable public URL. The intended DigitalOcean Cloud Firewall allows TCP 443 from all IPv4 addresses and SSH on 22 from the owner's IP. |
| Host and TLS | One self-managed Ubuntu 24.04 LTS x86-64 DigitalOcean Droplet runs Docker Engine and Compose. nginx publishes 443, terminates Let's Encrypt TLS, sets the client IP used by the app and forwards HTTP and WebSocket upgrades to Node at 127.0.0.1:4321. Certbot uses a zone-scoped Cloudflare token for DNS validation. The deploy hook copies the renewed chain and key into the proxy's certificate directory and reloads nginx. |
| Game | One Node.js 24 process serves the same-origin HTTP API, allowlisted browser assets and Slide Relay sockets using `ws`. The client uses native JavaScript modules, HTML, CSS, Canvas and bundled pixel fonts. Daily and Practice use HTTP. Relay uses persistent WebSockets on the same public HTTPS port. |
| Identity | Guests use server-managed sessions. Google sign-in uses OpenID Connect via `openid-client`, a server-side code exchange with PKCE, and the exact callback `https://penicillion.io/auth/callback`. Account identity uses Google's issuer and subject. Credentials are in the restricted host file `/etc/penicillion/config/game.env`. |
| Persistent data | PostgreSQL 17 stores accounts, sessions, published content, solo runs, scores, Relay turns, deadlines and command receipts in a Docker named volume. The Node API enforces ownership and membership. The game uses a restricted role, while the one-off admin job migrates, grants privileges and seeds content with a separate role. Row-level security is planned. |
| Redis | Redis 7 coordinates rate limits, socket leases and post-commit room notifications. Redis persistence is disabled. Reconnecting Relay clients fetch the authoritative snapshot backed by PostgreSQL. Both stores use authenticated TLS on the private Docker network. |
| Configuration and recovery | Compose and operator scripts live in `/opt/penicillion/ops/droplet`. Its local `.env` selects the image, config directory and HTTPS binding. Credentials, private CA and service keys live under restricted host paths outside Git and the web root. The host plan includes daily Droplet backups. Scripts support encrypted off-host PostgreSQL dumps using restic, restore drills, a backup heartbeat and daily calendar refill. Installation and successful execution of those scheduled jobs still need host evidence. |

## Ship a feature to the existing Droplet

For routine updates use the [GitHub Actions deployment guide](ACTIONS-DEPLOY.md). Each passing main commit gets a rehearsed AMD64 candidate and waits for the owner’s production approval. Install the outbound release timer once on the host.

## Manual release and recovery

1. **Develop locally.** Use the [feature guide](../AGENTS.md) to run the game and playtest the affected mode. Merge the reviewed change and check that **Game verification** passed for the exact commit on main. The workflow runs game, content, recovery and Chromium tests. Manual runs and version tags package ARM64 images. Updating main or creating a tag leaves the running Droplet image in place. [GitHub workflow](../.github/workflows/local-checks.yml)
2. **Package on the build machine.** Select the full tested commit SHA. Use the [release build commands](../ops/droplet/README.md#prepare-and-transfer-the-image) to build the production target for linux/amd64 from that commit, tag it with the revision, save it and compute SHA-256. Record the image ID and platform. Transfer the archive and checksum with scp into a new release directory on the Droplet. Verify the checksum against the build machine, load the image with Docker and compare the loaded ID and platform. If tracked deployment files changed, review and stage their matching revision too. Preserve the host's existing .env and private configuration.
3. **Select the release on the Droplet.** In `/opt/penicillion/ops/droplet`, record the current `GAME_IMAGE` tag and retain the old image. Edit just `GAME_IMAGE` in `.env` to the new verified tag. Run `sudo docker compose config --quiet`. For an app-only change with the same schema, grants, content and Compose services, apply it with `sudo docker compose up -d --no-deps --wait game`. This replaces the game container and reuses the database, cache, proxy and TLS configuration.
4. **Handle releases that change stored data or infrastructure.** For schema, grants or content changes, take a verified database backup first. Check compatibility with running and rollback versions. Run `sudo docker compose run --rm -T admin` for the new tag, then start the new game. The job applies migrations and grants, publishes the bundled edition and refills the calendar. If a migration is incompatible with live writers, schedule a maintenance window and stop the game before migrating. For changes to the proxy, private configuration or service definitions, follow the [full Compose runbook](../ops/droplet/README.md) and apply the affected services. Keep the existing Compose project and persistent volume throughout.
5. **Verify through the public hostname.** Run `curl -fsS https://penicillion.io/health/ready`. Open the site in a fresh browser tab and exercise the changed feature. For multiplayer, join from two sessions, submit an answer and check the handoff and reconnect. Test a real Google callback for identity changes. Record the deployed commit, image ID, time and result. With a single game container, players can see a brief interruption during replacement. Active Relay sockets disconnect and server-side deadlines continue to elapse. Prefer a gap between games.
6. **Roll back if needed.** For an app-only release, restore the recorded `GAME_IMAGE`, rerun the game-only Compose command and repeat the health and feature checks. For a release that changed storage or configuration, verify the previous image can read the current data and restore compatible deployment files as needed. An image rollback cannot undo a migration. If a database restore is required, preserve current data and identify which writes occurred since the backup before choosing a recovery point. [Restore procedure](../ops/droplet/README.md#start-and-maintain-the-pilot)

Ordinary feature releases reuse the existing domain, firewall, OAuth client and certificate.
