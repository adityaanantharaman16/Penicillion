# Hosting, privacy and scale

Decision proposal, 12 November 2026. The game runs locally. The owner requested a discussion and will approve deployment separately. This document authorizes no provisioning, credentials, DNS changes or spending.

## Recommended first environment and budget

For an invitation-only pilot, use DigitalOcean App Platform in New York, with two always-on instances of the Node **web service**, managed PostgreSQL and managed Valkey (compatible with Redis). A single HTTPS origin can serve the UI, API and authenticated WebSocket upgrades. The current Node, PostgreSQL and Redis design fits this topology. The existing [AWS deployment design](../ops/DEPLOYMENT.md) remains an alternative for a larger multi-AZ launch. Its earlier $450–850/month estimate assumes a substantially different availability and networking configuration and needs a fresh quote if selected.

## Slide Relay and provider-specific work

Each participant holds a secure WebSocket to one instance. On an answer or expiry, the worker locks the room in PostgreSQL, checks the turn and command ID, commits one result and publishes a room notification through Valkey. Each subscribed instance reads the committed state and sends the appropriate player view to its connected browsers. Reconnecting to a different instance recovers the current turn, lives, meter and deadline. The browser animates locally. Sticky sessions and a network message for every animation frame are unnecessary. [Game architecture](../ops/ARCHITECTURE.md) · [DigitalOcean WebSocket sample](https://github.com/digitalocean/sample-websocket)

Before a hosted trial, prepare these changes locally:

- Select the production game image target explicitly. The current delivery archive contains Linux ARM64 game and nginx images intended for the AWS design. Build and test a compatible image for the selected platform, preferably a multi-architecture release including AMD64. Route the provider's TLS ingress to the web service's configured port, bind on its container interface, and verify host/origin validation, test-only issuer rejection and the production readiness probe. The AWS nginx configuration assumes a loopback sidecar and CloudFront headers.
- Make the proxy trust boundary explicit. Accept the platform-injected client address only at the trusted ingress, remove untrusted forwarding fields and prevent a direct path to the worker. Test spoofed and repeated headers, HTTPS callbacks and WSS upgrades before depending on IP limits. [DigitalOcean client IP header](https://docs.digitalocean.com/support/where-can-i-find-the-client-ip-address-of-a-request-connecting-to-my-app/)
- Put both managed stores on a matching private network (NYC app / NYC1 VPC). Allowlist only the app's private egress and necessary restricted maintenance jobs. Use verified server certificates for PostgreSQL and Valkey and test CA rotation. A 2 GiB PostgreSQL plan lists 47 available backend connections. Start at six per web instance and budget for old and new replicas during rollout, migrations and operations. Increase from measurements of pool waits and DB saturation. [Private networking](https://docs.digitalocean.com/products/app-platform/how-to/enable-vpc/) · [Connection limits](https://docs.digitalocean.com/products/databases/postgresql/details/limits/)
- Run migrations and content publication once as a separate job with its own credential. Schedule issue refills and alert before the published horizon runs low. Pin the reviewed release and require a deliberate promotion. Disable automatic production deployment on Git pushes. Preserve backward compatibility across rolling releases.

Use encrypted **runtime-only** secrets scoped to each server component for DB and Valkey credentials, OIDC client secret and the session HMAC key. Keep the migration credential out of the web process. Give CI independent disposable credentials for tests. A production credential must never enter browser JS, source maps, a client build variable, a static directory, an image layer or a build log. Use sentinel values in a release test and inspect browser assets, HTTP bodies, logs and image history for leaks. Request dotfiles, environment variants, source files and the private release JSON over HTTP and verify denial. Rotate credentials and rehearse session revocation. **Keep Google OpenID Connect and guest play for the pilot.** Guests can play immediately. Signed-in accounts support persistent identity across devices, history claims and friend groups. Register the exact HTTPS callback and verify sign-in, sign-out, claim collisions and deletion in staging. Only the server exchanges the authorization code. Separate test and production registrations. ## Database authorization and row-level security

Today the API checks ownership and membership, and the runtime has broad SELECT privileges plus enumerated writes. The schemas currently define no RLS policies. Add PostgreSQL RLS as a second line of defense for player-scoped data. Limit columns separately for receipts, hidden fuses, sessions and answer keys. [Runtime grants](../ops/runtime-grants.sql) · [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

| Rows | Proposed access and exceptions |
| --- | --- |
| Solo runs, rounds, outcomes, command receipts, seen history, unlocks and missing-answer reports | Owner-only access, joining child rows to their run. Limit private reports to submitter operations and editorial review. Give leaderboard aggregates, voluntary sharing and guest-to-account claims narrow, separately audited paths. |
| Groups, memberships, blocks, bans and invitations | Active membership for group reads, owner or designated role for administration, actor-scoped blocks. Restrict invite redemption to a validated token operation. Verify kicks, revoked invitations and changes in sharing immediately. |
| Rooms, seats, room events and command receipts | Seat membership and valid participation determine snapshot access. Only the submitting actor may replay their private receipt. Use narrowly privileged operations for joining, matching, rematch and the cross-player turn update. Keep private fuse and answer-history internals behind explicit projections. |
| Sessions, identities, login attempts, unpublished content, future issues and editorial review | Restrict by role, operation and returned columns. Identity lookup occurs before the actor context exists. Give the login service a narrow lookup path. Give the game server internal access for judging and operators separate publication rights. |

Begin each actor-scoped transaction on one checked-out connection and set the actor context transaction-locally from the validated server session. Missing context denies access. Use both read/update predicates and write checks. The runtime role must be a non-owner without BYPASSRLS. Review FORCE ROW LEVEL SECURITY and privileged function ownership, fixed search paths and execution grants. A client-set actor ID is never authoritative. Give scheduled room expiry, cross-player settlement and aggregate computation explicit service privileges. Roll out by table family in an isolated database first. Exercise two guests, an account import, a spectator, a departed seat with an old receipt, guessed IDs, reused pooled connections, leaderboard opt-outs and a revoked session over an existing socket. Require correct responses and denials on both replicas.

## Rate limits and repeated reads

Keep shared limits across all instances. The [existing budgets](../ops/SECURITY.md) cover account and network abuse: guest creation 400/minute/network, login starts 5/minute/actor and 90/minute/network, room creation 5/10 minutes/actor, joins 10/minute/actor and 300/minute/network, answers 12/25 seconds/actor/mode, room commands 10/second/actor and 80/second/room, socket handshakes 30/minute/actor and four concurrent sockets/actor. HTTP writes also have an outer 90/minute/actor budget. Private reports already have a durable five-per-day actor limit.

For launch, test HTTP and socket paths against the same budgets, including repeated invalid commands, private-room probes and command replays. Add edge burst limits before expensive session lookup or OIDC callback work, bounded leaderboards and archive pagination, and tighter invite creation/redemption or report budgets if telemetry warrants. Measure legitimate refusals during ready-up, a school behind one IP, and mass reconnects. Return retry delays, reconnect with jitter, cap payloads and backpressure, and avoid charging identical retries twice in the game ledger. Monitor aggregate 429/503 counts by action. Keep raw answer text, IPs, tokens and room codes out of general analytics.

Start with existing Redis coordination and the existing epoch-based PostgreSQL standings cache. Instrument query count, latency and repeated keys before adding response caches. Proposed first candidates:

| Read | Key, lifetime and privacy |
| --- | --- |
| Repeated match lookups | Server-only positive mappings keyed by immutable release, prompt and normalized-term digest. Bound size, use about one hour TTL, and expire naturally on a new release namespace. Still check the round, duplicate concept, deadline and score transaction in PostgreSQL. Avoid caching arbitrary user misses initially. |
| Common aggregate reads | Key anonymous score distributions by issue, scoring release and committed standings epoch for 15–60 seconds. Apply participation thresholds and privacy gates on every request, then attach any personal result separately. Keep opt-in named boards out of this first cache. |
| Assets and private requests | Cache versioned static assets at the edge. Bypass shared HTTP caches for sessions, personalized Daily responses, histories, friend groups, invites and private room snapshots. Test with two players requesting the same URL. |

Use short TTLs with jitter, bound concurrent identical fills, record hit rate, memory and evictions. Isolate disposable caches from the noeviction limiter/lease service when cache volume competes for memory. Fall back to PostgreSQL on optional cache misses/outages. Preserve the existing 503 policy for operations that cannot enforce required limits. A lost notification recovers through room versions and a fresh authorized snapshot.

## Approval and proof before public access

1. **Local preparation.** Review the provider image/ingress changes, RLS migration, data retention and spend assumptions. Test secret handling and negative authorization cases with fake credentials. Bring region, proposed domain, exact SKUs, estimated spend and availability tradeoff to the owner.
2. **Only after approval for paid staging.** Exercise encrypted connections, OAuth and WebSocket upgrades on the real domain. Kill a worker mid-pass, replay the command, disconnect Valkey, and rotate a replica with active rooms. Restore PostgreSQL to an isolated cluster. Verify no duplicate pops, lost accepted outcomes or unauthorized reads.
3. **Measure pilot capacity.** Replay traffic from outside the datacenter, starting at expected pilot concurrency, then ramp toward the previous 1,500 solo plus 500 Relay seats for 30 minutes. Proposed gates: p95 solo server time under 300 ms, p95 relay commit-to-peer under 500 ms, fewer than 1% unexpected errors and zero score/turn integrity errors. Track DB connections, lock waits, socket reconnects, cache memory, worker CPU and cost. Increase capacity where the first bottleneck appears. Local measurements are a baseline. [Capacity test](../evidence/load/CAPACITY.md) · [Final meter regression](../evidence/load/relay-meter.md)
4. **Public launch decision.** Present staging results, monthly quote, restore time, rollback rehearsal, on-call contact and billing alarms. Obtain the owner's approval for public traffic and DNS cutover.
