# Hosting Penicillion on Vercel Pro and Supabase

The owner selected Vercel Pro and Supabase on 12 November 2026 for a commercial pilot of roughly 10–15 simultaneous players across Daily, Practice and Slide Relay. The game runs locally today. This handoff records design work. Implementation, cloud provisioning, spend and launch await further instruction. The [project roadmap](ROADMAP.md) records progress and the [Slide Relay migration plan](SLIDE-RELAY-MIGRATION.md) details the multiplayer work. The earlier DigitalOcean estimates and [AWS runbook](../ops/DEPLOYMENT.md) are historical alternatives.

## Services and budget

| Component | Proposed responsibility |
| --- | --- |
| Vercel Pro | Serve allowlisted browser assets and same-origin Node HTTP functions for authentication, judging, scores, room commands and personalized reads. Place functions near the chosen Supabase region. Preserve the existing hash routes and API contract. |
| Supabase PostgreSQL | Source of truth for principals, sessions, scores, immutable content releases, issue calendar, room membership and command receipts. Use transaction pooling for request traffic with a restricted role and verified TLS. Use a separate direct or session connection for migrations and maintenance. |
| Supabase Realtime | Private room notifications. Browsers fetch an authorized snapshot from the API after a change. A browser never publishes an authoritative game outcome. |
| Scheduled work | Use Supabase Cron for due-room discovery and periodic cleanup. Run reviewed corpus publication and Daily calendar refill with a separate job identity. Record the result and alert if the scheduled horizon runs low. |

Budget assumption for one environment and one paid Vercel seat is **$20/month base** with Supabase Free. The owner selected Supabase but has not selected its tier. Free includes 200 simultaneous Realtime connections and 2 million monthly messages. It can pause after a week of inactivity. Supabase Pro starts at $25/month, bringing the combined starting estimate to **$45/month**. Requote seats, compute, backup retention, bandwidth, domain and overages before purchase. Monitor connection minutes, message fan-out, DB size, scheduled work and usage alerts. Vercel classifies ads as commercial use. Ad integration is a separate feature. ## Daily and Practice compatibility

Seven-round play, answer matching, scores, pixel scenes, resumable turns and the content model already work with HTTP and PostgreSQL. Neither solo mode needs a new game engine or a Realtime subscription. There is shared hosting work before either can run on this stack. [HTTP entry point](../server/app.mjs) · [Solo handler](../server/solo/index.mjs) · [Database access](../server/database.mjs)

1. Expose the existing request paths through a Vercel Node handler. The current entry point opens a listener, connects Redis and its subscriber, attaches Relay sockets and starts interval timers on import. Separate those lifecycles. Preserve ingress timestamping, allowed origin and host, CSRF, cookies, body limits and trusted client IP handling. When serving the HTML, preserve its CSP and script nonce behavior. Allow only the specific HTTPS and WSS endpoints needed by Realtime.
2. Apply the existing core and solo schemas, roles, grants and immutable release to an empty Supabase database. Test the migration a second time. Seed past and upcoming issues and schedule the nightly 35-day refill. For any approved import, preserve release IDs, pinned issues, runs and receipts. Treat local playtest accounts and scores as fixtures unless the owner explicitly requests an import.
3. Keep a small bounded connection pool per active runtime. Use one checked-out connection per transaction, preserve row locks and transaction-scoped actor identity, and avoid session-level settings or named prepared statements on the transaction pooler. Check connection exhaustion during overlapping requests. [Supabase connections](https://supabase.com/docs/guides/database/connecting-to-postgres)
4. Preserve shared guest creation, answer and login limits across cold starts. Move session, login-attempt and invitation expiry off process intervals. Keep Google OIDC, guest sessions and guest-to-account claims as the initial design. Register exact production callbacks only in the approved environment. Relay channel credentials have a separate purpose from a game login. Clerk or a full Supabase Auth conversion would be a separate identity decision. [Identity](../server/identity.mjs) · [Limits](../server/limits.mjs)
5. Verify a full ranked Daily and timed and untimed Practice. Cover resume on a new function instance, a retried answer, a timeout, Eastern midnight and its grace window, private recap, archive and guest claim. Compare points, persisted outcomes and unrevealed answer access with the local build. [Solo browser test](../scripts/ci/solo.browser.mjs)

## Data, secrets and recovery

Only the browser assets belong in the public output. Keep the corpus, future issues, sessions, room events, connection strings, signing material, OAuth secrets and migration credentials on the server. Restrict privileged credentials to the job that needs them. Browser Realtime access uses the project public identifier, publishable key and a short-lived scoped user token. Never bundle environment files, service-role keys or private keys. Set environment-specific secrets in the provider settings, separate preview data and credentials, and avoid private data in builds, client bundles, source maps and logs. Check public routes and artifacts using fake sentinel credentials. [Supabase API keys](https://supabase.com/docs/guides/api/api-keys) · [Vercel sensitive variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables)

Limit operator access with MFA. Agree on account deletion, report retention and the acceptable loss of recent scores. For a Free pilot, schedule encrypted logical backups to restricted storage outside the project and test a restore. Price optional storage separately. On Pro, verify the actual backup window and restore procedure. Exercise restoration of scores, pinned issues, room receipts, policies and grants into an isolated project. [Supabase backups](https://supabase.com/docs/guides/platform/backups)

## Database authorization and row-level security

Today the API checks ownership and membership, and the runtime has broad SELECT privileges plus enumerated writes. The game migrations currently define no RLS policies. Supabase also exposes a Data API by default in many configurations. Disable it if unused or restrict its exposed schemas, revoke implicit browser-role grants and review default privileges for new tables before loading the bank. Add PostgreSQL RLS as a second line of defense for player-scoped data. Limit columns separately for receipts, hidden fuses, sessions and answer keys. [Runtime grants](../ops/runtime-grants.sql) · [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

| Rows | Proposed access and exceptions |
| --- | --- |
| Solo runs, rounds, outcomes, command receipts, seen history, unlocks and missing-answer reports | Owner-only access, joining child rows to their run. Limit private reports to submitter operations and editorial review. Give leaderboard aggregates, voluntary sharing and guest-to-account claims narrow, separately audited paths. |
| Groups, memberships, blocks, bans and invitations | Active membership for group reads, owner or designated role for administration, actor-scoped blocks. Restrict invite redemption to a validated token operation. Verify kicks, revoked invitations and changes in sharing immediately. |
| Rooms, seats, room events and command receipts | Seat membership and valid participation determine snapshot access. Only the submitting actor may replay their private receipt. Use narrowly privileged operations for joining, matching, rematch and the cross-player turn update. Keep private fuse and answer-history internals behind explicit projections. Authorize private Broadcast subscriptions separately through realtime.messages policies. |
| Sessions, identities, login attempts, unpublished content, future issues and editorial review | Restrict by role, operation and returned columns. Identity lookup occurs before the actor context exists. Give the login service a narrow lookup path. Give the game server internal access for judging and operators separate publication rights. |

Begin each actor-scoped transaction on one checked-out connection and set the actor context transaction-locally from the validated server session. Missing context denies access. Use both read/update predicates and write checks. The runtime role must be a non-owner without BYPASSRLS. Review FORCE ROW LEVEL SECURITY and privileged function ownership, fixed search paths and execution grants. A client-set actor ID is never authoritative. Give scheduled room expiry, cross-player settlement and aggregate computation explicit service privileges. Roll out by table family in an isolated database first. Exercise two guests, an account import, a spectator, a departed seat with an old receipt, guessed IDs, reused pooled connections, leaderboard opt-outs and a revoked session over an existing socket. Require correct responses and denials across independent function invocations.

## Rate limits and repeated reads

Keep shared limits across all function invocations. The [existing budgets](../ops/SECURITY.md) cover account and network abuse: guest creation 400/minute/network, login starts 5/minute/actor and 90/minute/network, room creation 5/10 minutes/actor, joins 10/minute/actor and 300/minute/network, answers 12/25 seconds/actor/mode, room commands 10/second/actor and 80/second/room, socket handshakes 30/minute/actor and four concurrent sockets/actor. HTTP writes also have an outer 90/minute/actor budget. Private reports already have a durable five-per-day actor limit.

For launch, enforce command budgets on the HTTP API and connection/subscription budgets at the Realtime authorization boundary. Test both paths, including repeated invalid commands, private-room probes and command replays. Add edge burst limits before expensive session lookup or OIDC callback work, bounded leaderboards and archive pagination, and tighter invite creation/redemption or report budgets if telemetry warrants. Measure legitimate refusals during ready-up, a school behind one IP, and mass reconnects. Return retry delays, reconnect with jitter, cap payloads and backpressure, and avoid charging identical retries twice in the game ledger. Monitor aggregate 429/503 counts by action. Keep raw answer text, IPs, tokens and room codes out of general analytics.

The local baseline uses Redis. For the pilot, budget for PostgreSQL-backed atomic limit counters and connection leases with expiry, and benchmark their cleanup and contention. Adapt readiness checks and the mandatory REDIS_URL startup dependency only after equivalent limits pass. The existing versioned PostgreSQL standings cache can serve the pilot. Redis remains an option for measured pressure on counters or repeated reads as traffic grows. Instrument query count, latency and repeated keys before adding response caches. Proposed first candidates:

| Read | Key, lifetime and privacy |
| --- | --- |
| Repeated match lookups | Server-only positive mappings keyed by immutable release, prompt and normalized-term digest. Bound size, use about one hour TTL, and expire naturally on a new release namespace. Still check the round, duplicate concept, deadline and score transaction in PostgreSQL. Avoid caching arbitrary user misses initially. |
| Common aggregate reads | Key anonymous score distributions by issue, scoring release and committed standings epoch for 15–60 seconds. Apply participation thresholds and privacy gates on every request, then attach any personal result separately. Keep opt-in named boards out of this first cache. |
| Assets and private requests | Cache versioned static assets at the edge. Bypass shared HTTP caches for sessions, personalized Daily responses, histories, friend groups, invites and private room snapshots. Test with two players requesting the same URL. |

Use short TTLs with jitter, bound concurrent identical fills, record hit rate, memory and evictions. Isolate disposable caches from the noeviction limiter/lease service when cache volume competes for memory. Fall back to PostgreSQL on optional cache misses/outages. Preserve the existing 503 policy for operations that cannot enforce required limits. A lost notification recovers through room versions and a fresh authorized snapshot.

## Acceptance and owner decisions

Once implementation is requested, develop locally against isolated test data. Keep existing Compose play and CI as the comparison point. Prove cold-start solo requests and the private two-player Relay prototype first. Check access denials, shared limits, backups and client bundles. Use local provider tooling where possible and mark hosted-only behavior unverified.

Before connecting Git to Vercel or provisioning a Supabase project, obtain staging and spend approval. Record the chosen region, plan, domain, alerts and backup choice. Isolate previews from production. In approved staging, run the solo suite and Relay playtests, then a 30-minute mixed run at 30 concurrent players. Measure peak DB connections, answer latency, wake-up delays and unauthorized reads. Demonstrate a backup restore and rollback to a compatible application version. Present results, remaining limits and the revised bill for separate public-launch approval.
